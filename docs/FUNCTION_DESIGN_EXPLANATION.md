# AI Fiction to Script 功能设计与技术实现说明

本文围绕项目当前版本的主要功能，说明每一部分为什么这样设计、为什么选用对应技术、功能如何实现、交互如何设计，以及后续可以如何扩展。文档面向项目答辩、路演讲解、技术评审和后续维护者阅读。

## 1. 项目定位与总体设计目标

`AI Fiction to Script` 的核心目标是把多章节小说快速改编为结构化、可编辑、可追踪版本的剧本草稿。它不是单纯把小说“总结一下”，也不是只做一个聊天式生成页面，而是试图解决小说改编工作流里的几个具体问题：

1. 小说原文通常很长，直接一次性丢给模型生成剧本容易丢上下文、结构混乱、格式不可控。
2. 剧本创作需要反复修改，不能每次都从头生成；用户需要保留历史版本、对比差异、局部重写。
3. 生成结果需要能被人编辑，也要能被程序验证，所以不能只输出一段普通文本。
4. 用户既可能是开发者，也可能是内容创作者，因此需要同时提供 CLI 和 Web 工作台。
5. 模型调用速度和成本不可忽略，需要有 Mock、本地启发式、Qwen 在线模型、缓存、异步任务等组合能力。

因此项目的总体设计不是“前端调用一次大模型，然后展示结果”，而是拆成“输入解析 -> 章节理解 -> 故事设定 -> 大纲规划 -> 剧本文本生成 -> YAML 结构化 -> 质量检查 -> 版本保存 -> Web/CLI 交互”的流水线。

### 为什么采用分层流水线

分层流水线的主要原因是可控性。小说到剧本不是一个单步任务，它天然包含多个中间成果：

- 章节摘要决定模型是否理解原文。
- Story Bible 决定人物、地点、关系和主题是否稳定。
- Outline 决定剧情结构是否合理。
- Scene Plan 决定每一场/每一章要完成什么戏剧任务。
- Script 才是最终可读的剧本文本。
- Quality Report 负责暴露不确定性和可修改建议。

如果这些中间层不落盘，后续很难定位问题。例如生成结果不好时，不知道是章节解析失败、人物关系错误、场景计划不合理，还是剧本文本生成不稳定。当前项目把中间产物保存在版本目录中，便于调试、回放和局部重生成。

### 总体架构

当前系统可以理解为五层：

| 层级 | 主要职责 | 代表模块 |
| --- | --- | --- |
| 输入层 | 读取 txt/doc/docx/目录，拆分章节，清洗文本 | `ChapterParser` |
| 编排层 | 串联章节分析、Story Bible、大纲、剧本生成和质检 | `AdaptationEngine`、`WorkbenchService` |
| 模型层 | 封装 Mock/Qwen/Hybrid 调用和 prompt 逻辑 | `BaseAIClient`、`QwenAIClient`、`MockAIClient`、`PromptBuilder` |
| 数据层 | 定义结构化剧本 Schema、版本保存、YAML 导入导出 | `ScreenplayDocument`、`VersionStore`、`yaml_service` |
| 交互层 | CLI 命令、HTTP API、Web 静态页面、异步任务流 | `cli.py`、`web/server.py`、`web/static/*` |

这种结构的好处是每层职责清晰：CLI 和 Web 都复用同一套服务；模型供应商可以替换；输出格式可验证；版本存储可以从本地文件演进到数据库或对象存储。

## 2. 技术栈选择

### Python 3.12

项目主语言选择 Python，是因为 AI 编排、文本处理、YAML/JSON 处理、命令行工具和轻量 Web 服务都属于 Python 生态擅长的范围。

选择 Python 3.12 的原因：

- 类型标注和标准库能力更完善，适合维护结构化数据模型。
- 与 `pydantic`、`typer`、`httpx`、`pyyaml` 等依赖兼容性好。
- 开发速度快，适合快速验证 AI 工作流。
- 文本处理成本低，便于处理中文小说、章节切分、提示词拼接。

项目没有选择 Java/Spring 或 Node 全栈，是因为当前核心难点不是高并发业务系统，而是 AI 生成链路的稳定性、结构化输出和本地工作流。Python 能降低实现成本。

### Pydantic v2

项目用 Pydantic 定义 `ScreenplayDocument`、`AdaptationRequest`、章节分析、版本记录等数据模型。

选择 Pydantic 的原因：

- 能同时承担运行时数据校验和 JSON Schema 导出。
- 对复杂嵌套结构支持好，适合剧本 YAML 这种多层文档。
- 可以通过 `model_validator` 做跨字段校验，例如章节数量、ID 唯一性、引用合法性。
- 可以和 YAML/JSON 很自然地互相转换。

在这个项目里，Pydantic 的价值不只是“类型声明”，而是保证 AI 输出不会任意漂移。AI 生成的内容天然不稳定，必须用强约束把它收束成系统能继续处理的结构。

### YAML + JSON Schema

最终剧本使用 YAML，而不是纯 JSON 或 Markdown。

设计原因：

- YAML 对人更友好，作者和编辑可以直接阅读、修改。
- 相比 Markdown，YAML 更容易被程序解析、验证和差异对比。
- 相比 JSON，YAML 对长文本、多层剧本结构更可读。
- JSON Schema 可以从 Pydantic 模型导出，方便第三方工具或后续前端校验。

这里的关键权衡是：YAML 不是最严格的机器格式，但它能兼顾“人类可编辑”和“机器可验证”。对于剧本草稿工具，这是更合适的平衡点。

### Typer + Rich

CLI 使用 Typer 和 Rich。

Typer 的优势：

- 基于类型标注生成命令行参数，命令定义简洁。
- 适合快速扩展多个子命令，例如 `adapt`、`quick`、`validate`、`web`、`diff`。
- 错误提示和帮助文档比手写 argparse 更清晰。

Rich 的作用：

- 让命令行输出更易读，例如版本列表表格、成功/警告信息。
- 对中文内容和状态展示更友好。

CLI 的设计目标不是替代 Web，而是服务开发者、批处理和自动化测试。内容创作者可以用 Web，开发者可以用 CLI。

### ThreadingHTTPServer + 原生 HTML/CSS/JavaScript

Web 服务使用 Python 标准库 `ThreadingHTTPServer`，前端使用原生 HTML/CSS/JavaScript。

为什么没有选 FastAPI、Flask、React 或 Vue：

- 当前项目需要的是本地工作台和轻量 API，不是复杂 SaaS 平台。
- 标准库 HTTP 服务部署简单，依赖少，适合教学、演示和离线运行。
- 原生前端足够支撑当前交互：上传、表单、项目列表、任务状态、YAML 预览、版本对比、场景重生成。
- 少引入框架可以降低环境配置成本，用户只要安装 Python 包即可运行。

这个选择的代价是前端组件化和大型状态管理能力较弱。但对当前项目来说，核心风险在 AI 工作流，不在复杂前端工程。保持轻量可以让项目更容易运行和展示。

### httpx + OpenAI-Compatible API

模型调用使用 `httpx`，并面向 Qwen/DashScope 的 OpenAI-Compatible API。

选择原因：

- `httpx` 支持超时、连接配置、流式响应等能力，适合模型 API 调用。
- OpenAI-Compatible 接口降低供应商绑定，后续可以接入其他兼容模型。
- DashScope/Qwen 对中文长文本和中文剧本生成更适合，符合项目主要使用场景。

项目中还保留 `MockAIClient`，不是为了“模拟一下”这么简单，而是为了：

- 没有 API Key 时也能演示完整流程。
- 自动化测试不依赖外部网络和真实模型。
- 在模型不可用时能定位是服务逻辑问题还是模型调用问题。

### Redis、Nginx、Docker Compose

这些部署组件是可选增强，不是核心运行前提。

Redis 用于缓存项目列表、版本列表、版本详情、diff 等读操作。设计原因是 Web 工作台频繁读取版本数据，缓存可以降低本地文件系统反复解析 YAML 的开销。

Nginx 用作反向代理，提供更接近真实部署的访问方式，也方便处理静态资源、请求转发和统一入口。

Docker Compose 用来一键启动 App、Redis 和 Nginx，降低部署复现成本。对答辩或演示来说，`docker compose up --build` 比手动启动多个进程更稳定。

## 3. 数据模型与 YAML Schema 设计

### 为什么把剧本设计成 `ScreenplayDocument`

项目的核心数据对象是 `ScreenplayDocument`，它包含：

- `meta`：项目、标题、作者、剧本类型、模型信息。
- `source`：原始章节信息。
- `adaptation`：改编目标、节奏策略、风格指南。
- `story_bible`：人物、地点、时间线、主题、道具。
- `outline`：分幕和场景计划。
- `script`：最终剧本文本，按 act、scene、beat 组织。
- `quality`：质量评分、警告、修改建议、一致性检查。
- `extensions`：扩展字段。

这样设计的原因是剧本不是单一文本，而是一组互相关联的信息。把它们放在一个顶层文档里，可以让文件离开系统后仍然自描述。例如用户下载 YAML 后，仍然能知道这个剧本来自哪个小说、目标格式是什么、由哪个模型生成、有哪些质量警告。

### 为什么要拆出 `story_bible`

Story Bible 是剧作领域常见概念，表示故事设定集。项目单独设计这一层，是为了稳定生成过程。

如果每次生成场景都只给模型当前章节，模型很容易忘记人物关系、地点风格和主线冲突。Story Bible 把这些信息抽取出来，作为后续大纲规划和场景生成的共同上下文。

它带来的好处：

- 人物名称、性格、目标更一致。
- 地点和时间线更稳定。
- 场景重生成时可以只改局部，不破坏全局设定。
- 后续可以让用户单独编辑 Story Bible，再重新生成剧本。

### 为什么用稳定 ID 做引用

Schema 中大量使用 `chapter_id`、`character_id`、`location_id`、`scene_id`，而不是直接用名字互相引用。

原因是名字不稳定：

- 中文名可能重名。
- 用户可能改人物名。
- 模型可能生成别名。
- 同一个地点可能有不同表达。

稳定 ID 可以保证引用关系不受展示文案变化影响。例如 dialogue beat 中的 `speaker_ref` 指向 `character_id`，即使人物显示名被改掉，引用仍然有效。

### 为什么限制 Beat 类型

`Beat` 的类型限制为：

- `action`
- `dialogue`
- `transition`
- `narration`

这是有意收敛复杂度。剧本表达可以非常复杂，但第一版工具要保证可编辑、可验证、可渲染。四类 beat 已经能覆盖动作、对白、转场和旁白，同时不会让模型输出过多无法处理的自定义类型。

后续如果要扩展短剧、分镜、拍摄计划，可以在保持兼容的前提下增加类型或放到 `extensions`。

### 为什么设置最少三章

当前 Schema 要求 `source.chapter_count >= 3`，并且 `source.chapters` 至少三章。

设计原因：

- 项目定位是“多章节小说改编”，不是单段文本扩写。
- 至少三章才有基本的开端、推进和转折，适合形成剧本结构。
- 这能避免用户输入过短时生成看似完整但实际信息不足的剧本。
- 也方便质量检查和大纲规划有足够素材。

这不是技术限制，而是产品边界。短输入可以后续作为“片段扩写”或“单场景生成”单独设计。

## 4. 小说输入与章节解析设计

### 功能目标

输入层负责把用户提供的小说材料转换成统一的 `ParsedChapter` 列表。支持的输入形式包括：

- 单个文本文件。
- Word 文档。
- 包含多个章节文件的目录。
- Web 页面粘贴文本或上传文件后生成的临时文本。

### 为什么要先做章节解析

小说通常比模型上下文更长，即使模型支持长上下文，一次性输入全部内容也会带来几个问题：

- 成本高。
- 速度慢。
- 模型容易忽略中间细节。
- 后续无法定位某个场景来自哪一章。

章节解析让系统可以按章节进行摘要和生成。每个场景都保留 `chapter_refs` 和 `source_refs`，便于用户回看来源。

### 实现思路

`ChapterParser` 的职责是：

1. 判断输入是文件还是目录。
2. 读取文本内容。
3. 按章节标题、文件边界或规则切分。
4. 为每章生成稳定的 `chapter_id`。
5. 保存标题、正文、引用路径、摘录等字段。

这种实现比直接把文件内容传给模型更可靠，因为后续所有环节都可以基于 `chapter_id` 做追踪。

### 交互设计

Web 端给用户两种输入方式：

- 上传小说文件。
- 直接粘贴小说正文。

这样设计是为了覆盖两类使用场景：已有完整文档的用户可以上传；临时测试或演示时可以直接粘贴。前端不会强迫用户同时填写两者，后端会统一解析成章节。

CLI 端则通过路径参数输入：

```powershell
novel2script quick examples/sample_novel.txt --provider mock
```

这种交互符合命令行批处理习惯，也便于测试。

## 5. 改编请求模型与预设设计

### 功能目标

`AdaptationRequest` 描述一次生成任务的意图，包括：

- 项目 ID、剧本标题、原小说标题、作者。
- 目标格式，如电视剧、短剧、电影、舞台剧。
- 类型和语气。
- provider 和 model name。
- 生成详细度。
- 改编目标、节奏策略、风格指南。

### 为什么需要请求模型

如果每个入口都自己拼参数，CLI、Web、异步任务和重生成会很快失控。统一请求模型有几个好处：

- CLI 和 Web 共用同一套生成参数。
- 版本保存时可以记录当时的请求，后续重生成可复现。
- 测试可以直接构造请求对象，不依赖前端表单。
- 增加模型选择、生成详细度等功能时只需要扩展模型字段。

### 生成详细度设计

当前详细度分为：

- `fast`：快速预览，章节上下文更短，beat 更少。
- `standard`：默认平衡。
- `detailed`：更长上下文和更多 beat，适合更完整草稿。

设计原因是 AI 生成存在速度、成本和质量的三角关系。用户在不同阶段需求不同：

- 演示或初筛时需要快。
- 正式初稿需要平衡。
- 深度打磨需要更丰富。

因此详细度不是简单前端选项，而是会影响 `chapter_context_chars`、`max_beats_per_scene`、温度等后端参数。

### 模型选择设计

Web 端支持从 Qwen/DashScope 的 `/models` 接口加载可用模型，也支持用户手动填写 API Key。

设计原因：

- 不同用户的账号可用模型不同。
- 写死模型名会导致环境差异下不可用。
- 让后端记录 `model_name`，可以在版本元信息中追踪生成来源。

模型选择不是只影响完整生成，也要影响 YAML 重生成和单场景重生成，所以请求模型里有统一的 `model_name` 和 `model_routing`。

## 6. AI 客户端设计

### 抽象接口

项目通过 `BaseAIClient` 定义模型能力，核心方法包括：

- `analyze_chapter`
- `build_story_bible`
- `plan_outline`
- `generate_scene`
- `generate_script`
- `review_document`

### 为什么要抽象 AI Client

AI 供应商和调用方式很容易变化。如果业务逻辑直接写死 Qwen API，后续切换模型、测试 Mock、局部使用启发式都会很困难。

抽象后有三个实现方向：

- `MockAIClient`：本地可运行、测试稳定。
- `QwenAIClient`：真实模型生成。
- `HybridAIClient`：部分步骤用本地/Mock，关键文本生成用 Qwen。

### MockAIClient 的设计价值

Mock 不是临时测试代码，而是系统可靠性的基础。

它解决的问题：

- 没有 API Key 也能跑通完整流程。
- 测试不受网络和模型输出波动影响。
- 可以快速验证前端、版本库、Schema、CLI 是否正常。
- 在演示时可以避免模型调用失败导致项目不可展示。

### QwenAIClient 的设计价值

Qwen 更适合中文小说和中文剧本生成。通过 OpenAI-Compatible API 接入，可以让代码结构更通用。

Qwen 客户端主要负责：

- 构造请求。
- 处理超时。
- 解析响应。
- 支持流式生成。
- 将模型输出转成项目内部结构。
- 对模型输出做容错和回退。

### HybridAIClient 的设计价值

在 Web 模式下，项目不是所有步骤都必须让 Qwen 完成。章节摘要、大纲规划等步骤可以由本地启发式或 Mock 快速完成，把真正需要语言创造力的部分交给 Qwen。

这样设计的原因：

- 降低整体等待时间。
- 降低模型调用成本。
- 减少长链路中某一步模型不稳定导致整体失败的概率。
- 保留核心生成质量。

### 为什么要“先生成剧本文本，再结构化 YAML”

当前版本把 Qwen 完整草稿和场景重生成流程调整为：先生成可读剧本文本，再在本地结构化为 YAML。

原因是直接要求模型输出完整 YAML 容易出现：

- 缩进错误。
- 字段缺失。
- 多余字段。
- 中文长文本被截断。
- YAML 符号与剧本文字冲突。

先生成剧本文本可以让模型专注创作表达；本地结构化可以让程序负责格式稳定。这是把“创造性任务”和“确定性结构化任务”分开的设计。

## 7. PromptBuilder 设计

### 功能目标

`PromptBuilder` 负责为不同阶段生成提示词：

- 章节分析提示词。
- Story Bible 构建提示词。
- 大纲规划提示词。
- 场景生成提示词。
- YAML 重生成提示词。
- 单场景重写提示词。

### 为什么不把 prompt 写在 AI Client 里

模型调用和提示词构建是两个职责：

- AI Client 负责“怎么调用模型”。
- PromptBuilder 负责“让模型做什么”。

拆开以后有几个好处：

- prompt 可以单独测试。
- 更容易针对不同任务调整提示词。
- 后续可以为不同模型准备不同 prompt 模板。
- AI Client 不会变成一个又长又难维护的类。

### Prompt 设计原则

当前提示词设计围绕几个原则：

1. 明确输入边界：告诉模型当前处理的是章节、全局设定、场景还是已有 YAML。
2. 明确输出目标：要求模型生成剧本文本、场景内容或结构化信息。
3. 保留约束：目标格式、语气、详细度、章节引用、人物设定。
4. 避免过度自由：减少模型输出和系统 Schema 不匹配的概率。
5. 支持中文创作：提示词强调自然口语化对白、剧情节奏和中文短剧/剧本表达。

## 8. 改编流水线设计

### 核心流程

`AdaptationEngine.run()` 的核心流程是：

1. 解析输入章节。
2. 校验章节数量和文本有效性。
3. 并发分析每个章节。
4. 构建 Story Bible。
5. 规划 Outline。
6. 将大纲标准化为按章节推进的剧本单元。
7. 并发生成场景。
8. 组装 Script。
9. 同步 Outline 与 Script。
10. 创建 `ScreenplayDocument`。
11. 运行质量检查。
12. 保存版本和中间产物。

### 为什么章节分析和场景生成要并发

章节分析之间相对独立，场景生成之间也相对独立，因此可以使用 `ThreadPoolExecutor` 并发执行。

这样设计的原因：

- 多章节小说串行处理会明显变慢。
- Python 的线程对 IO 型任务有效，模型调用通常是网络 IO。
- 并发数限制为最多 6，避免过多请求压垮本地或模型服务。

### 为什么要标准化为连续章节结构

早期剧本常见三幕结构，但小说改编时，用户更关心“每章对应一段可读剧本”。当前版本将大纲标准化为 `continuous_sequence`，并保证每章生成一个完整剧本单元。

设计原因：

- 小说用户更容易理解“第几章生成了什么”。
- 方便追踪来源章节。
- 避免模型把同一章拆成多个碎片，导致 Web 端比较和重生成复杂。
- 更适合短剧/网文改编的连续推进方式。

这不是否定三幕结构，而是当前产品阶段更重视原文追踪和版本编辑。

### 质量检查设计

`QualityChecker` 负责检查：

- Schema 是否符合要求。
- 引用关系是否一致。
- 是否存在章节、人物、地点等断裂。
- 生成结果是否有警告和修改建议。

质量报告不是为了给一个绝对分数，而是为了告诉用户“这个 AI 草稿还有哪些风险”。AI 生成内容不能默认可信，必须把不确定性显式展示出来。

## 9. 版本管理设计

### 功能目标

版本管理是项目区别于普通生成工具的关键能力。每次生成、保存编辑、YAML 重生成、单场景重生成都会创建一个新版本。

本地目录结构大致为：

```text
.novel2script/
  project-id/
    index.json
    versions/
      v0001/
        screenplay.yaml
        intermediates/
          request.json
          chapters.json
          chapter_analyses.json
          story_bible.json
          outline.json
```

### 为什么不用覆盖保存

剧本创作是反复试错过程。覆盖保存会导致：

- 无法回退。
- 无法比较模型生成差异。
- 无法知道某次修改用了什么参数。
- 单场景重生成可能破坏原版本。

所以项目采用不可变版本目录：每次修改产生新的 `v000x`。这样更接近 Git 的思路，也更适合 AI 生成工作流。

### 为什么保存中间产物

只保存最终 YAML 不够。中间产物可以回答这些问题：

- 当时的请求参数是什么？
- 原始章节如何被解析？
- 章节摘要是什么？
- Story Bible 如何影响生成？
- 大纲和最终剧本是否一致？

保存中间产物使后续重生成、调试和审计更可控。

### Diff 设计

版本对比使用 YAML 文本 diff。原因是用户最关心的是“文件实际变了什么”，而不是抽象对象差异。

文本 diff 的好处：

- 直观。
- 易于在 CLI 和 Web 端展示。
- 对 YAML 文件天然适配。

后续可以扩展为结构化 diff，例如只比较人物、场景、对白。

## 10. Web 工作台设计

### 功能定位

Web 工作台面向非开发者和演示场景，提供可视化操作入口：

- 创建剧本生成任务。
- 上传文件或粘贴文本。
- 选择 provider、模型、类型、语气、详细度。
- 查看项目列表和版本列表。
- 加载版本详情。
- 预览 YAML 和剧本内容。
- 下载 YAML。
- 保存编辑后的 YAML。
- 对比版本。
- 从 YAML 重生成。
- 单场景重生成。
- 查看异步任务状态。

### 为什么采用侧边栏 + 主工作区布局

项目工作台天然有两个层次：

- 左侧是项目和版本导航。
- 右侧是当前版本的生成、预览、编辑和重生成。

侧边栏布局的优点：

- 项目列表常驻，用户随时可以切换版本。
- 主区域留给大文本和预览，不被导航打断。
- 状态徽标、语言选择、刷新等全局操作放在侧边栏更符合工作台习惯。

### 为什么表单不预填示例值

当前版本移除了标题、作者、原小说标题、类型等字段的默认示例填充值。

原因是预填示例在演示时看起来方便，但实际使用会带来误导：

- 用户可能忘记修改，导致生成结果带错误元数据。
- 自动化测试和实际交互容易混淆默认值与用户输入。
- 对创作工具来说，空字段比错误字段更安全。

因此表单保留输入能力，但不强行填入示例内容。

### 为什么采用异步任务

完整剧本生成和 YAML 重生成可能很慢。如果使用同步请求：

- 浏览器可能等待超时。
- 用户看不到进度。
- 服务端异常不容易反馈。

异步任务的设计是：

1. 前端提交请求。
2. 后端创建 task_id。
3. 后台线程执行生成。
4. 前端轮询或通过 SSE 读取任务状态。
5. 完成后返回版本信息。

这种方式能让 Web 交互更稳定，也为后续任务队列化打基础。

### 为什么支持 SSE

SSE 适合服务端单向推送任务状态。相比 WebSocket，它更轻量：

- 浏览器原生支持。
- 实现简单。
- 适合“服务端不断告诉前端任务进度”的场景。
- 不需要双向实时通信。

当前项目的任务状态只需要从服务端推给前端，因此 SSE 足够。

### 为什么支持 YAML 编辑保存

AI 生成的 YAML 是草稿，不是最终稿。用户需要直接改内容，然后保存为新版本。

这样设计的原因：

- 尊重人类编辑在剧本创作中的主导地位。
- 修改后的 YAML 仍然经过 Schema 校验。
- 保存编辑不覆盖旧版本，方便回退。
- 后续可以基于人工编辑版本继续重生成。

## 11. CLI 设计

### 功能定位

CLI 面向开发者、测试人员和批处理用户。主要命令包括：

- `novel2script quick`
- `novel2script adapt`
- `novel2script validate`
- `novel2script list-versions`
- `novel2script diff`
- `novel2script regenerate-scene`
- `novel2script export-schema`
- `novel2script web`

### 为什么同时保留 CLI 和 Web

两类用户需求不同：

- 内容创作者需要可视化界面。
- 开发者需要脚本化能力。
- 测试需要可重复命令。
- 部署和演示需要快速启动 Web。

保留 CLI 还能让后端能力更容易被验证。如果一个功能只能通过前端触发，测试和调试成本会更高。

### `quick` 与 `adapt` 的区别

`quick` 是低门槛入口，尽量少填参数，适合快速跑通。

`adapt` 是完整入口，允许指定标题、作者、项目 ID、目标格式、类型、语气、provider、模型、详细度、输出路径和版本目录。

这样设计可以兼顾“第一次使用”和“正式生产”。

## 12. YAML 重生成设计

### 功能目标

用户可以上传已有剧本 YAML，让模型基于当前结构和内容重新生成一个新版本。

### 为什么需要 YAML 重生成

实际创作中，用户往往不是只从小说生成一次剧本，而是会：

- 修改已有 YAML。
- 想换一种语气。
- 想调整详细度。
- 想让模型基于已有剧本重新润色。

如果系统只支持“小说 -> 剧本”，就无法服务后续打磨流程。YAML 重生成让工具从一次性生成器变成迭代式创作工具。

### 实现思路

1. 前端上传或粘贴 YAML。
2. 后端解析为 `ScreenplayDocument`。
3. 提取已有 story、outline、script、request 信息。
4. 构造重生成提示词。
5. 调用模型生成新的剧本文本。
6. 本地结构化成新的 YAML。
7. 质量检查并保存为新版本。

### 交互设计

YAML 重生成作为独立入口，而不是隐藏在普通生成表单里。原因是两者输入不同：

- 普通生成输入小说。
- YAML 重生成输入已有剧本文件。

分开入口能减少用户误操作，也让页面状态更清晰。

## 13. 单场景重生成设计

### 功能目标

用户可以选择某个 `scene_id`，输入改写指令，只重生成该场景，并保存为新版本。

### 为什么需要单场景重生成

剧本修改通常是局部的。完整重生成会带来两个问题：

- 成本高、时间长。
- 可能破坏用户已经满意的部分。

单场景重生成的价值是精确修改。用户可以要求：

- 加强冲突。
- 减少旁白。
- 改写对白。
- 改变语气。
- 增加悬念。

### 实现思路

1. 加载指定项目和版本的 `ScreenplayDocument`。
2. 根据 `scene_id` 找到场景计划和对应章节。
3. 加载原始请求和章节上下文。
4. 应用用户改写指令、provider/model/tone/detail 覆盖。
5. 调用 AI 生成新场景。
6. 替换原场景。
7. 同步 outline 和 script。
8. 重新质量检查。
9. 保存为新版本。

### 为什么保存为新版本而不是直接改原版本

单场景重生成看似是小改动，但它仍然可能改变剧情逻辑。保存为新版本可以让用户比较新旧场景，满意再继续使用，不满意可以回退。

## 14. 缓存设计

### 功能目标

Web 工作台频繁读取：

- 项目列表。
- 版本列表。
- 版本详情。
- diff 结果。

如果每次都从磁盘读取 YAML 并解析，数据量大时会影响体验。缓存层用于减少重复读取。

### 为什么设计成可选 Redis

Redis 是可选能力，因为本地演示不应该强依赖外部服务。项目通过 `NullCacheStore` 和 `RedisCacheStore` 抽象缓存：

- 没有 Redis 时系统照常运行。
- 有 Redis 时自动缓存读接口。
- Docker Compose 可以自动启动 Redis。

这种设计避免了“为了性能优化牺牲易运行性”。

### 缓存失效设计

版本保存、删除、重生成后，相关项目缓存需要失效，否则用户会看到旧数据。缓存 key 使用项目维度前缀，便于按项目清理。

## 16. 测试设计

### 测试覆盖目标

当前测试覆盖：

- AI Client 行为。
- PromptBuilder 输出。
- CLI 命令。
- Pipeline 编排。
- WorkbenchService 服务逻辑。
- Web API。
- YAML/Schema 相关行为。

### 为什么测试重点放在服务层

AI 项目的风险不只在 UI，而在中间编排逻辑：

- 请求是否正确转换。
- 版本是否正确保存。
- 重生成是否保留上下文。
- Schema 是否能校验。
- Mock 和 Qwen 路径是否一致。

服务层测试能覆盖 CLI 和 Web 的共同核心，比只测前端点击更有价值。

### 为什么需要 Mock 模型测试

真实模型输出不可控，不能作为稳定单元测试基础。Mock 可以提供确定性输出，让测试验证系统逻辑，而不是验证某次模型回答。

## 18. 关键设计权衡

### 轻量 Web 服务 vs 完整 Web 框架

当前选择轻量标准库服务，是为了减少依赖和部署复杂度。缺点是路由、中间件、认证、文件上传能力都需要手写。后续如果要做多人协作或云端服务，可以迁移到 FastAPI。

### YAML 可编辑性 vs 格式严格性

YAML 对人友好，但格式比 JSON 更容易因缩进出错。项目通过 Pydantic 校验和 JSON Schema 导出来弥补这一点。

### 本地文件版本库 vs 数据库

本地文件版本库简单透明，适合个人和演示。缺点是多人协作、并发写入和权限管理较弱。后续商业化或团队协作可以迁移到 SQLite/PostgreSQL + 对象存储。

### Mock/Hybrid/Qwen 多路径 vs 实现复杂度

多模型路径增加代码复杂度，但换来测试稳定性、演示可靠性和成本控制。对 AI 工具来说，这是值得的。

### 按章节连续结构 vs 传统三幕结构

传统剧本更偏三幕，但小说改编工具的第一目标是来源可追踪和章节可编辑。当前选择按章节连续输出，更符合网文/短剧改编初稿阶段。

## 20. 总结

本项目的核心设计思想是：把小说改编这个复杂 AI 任务拆成可验证、可追踪、可迭代的工程流程。

技术上，项目选择 Python、Pydantic、YAML、Typer、ThreadingHTTPServer、Qwen API、Redis、Docker Compose，是为了在“容易运行”和“结构可靠”之间取得平衡。

功能上，项目同时支持 CLI 和 Web，既能满足开发者自动化，也能让内容创作者直接使用。版本管理、YAML 编辑、YAML 重生成和单场景重生成，让它不只是一次性生成工具，而是一个可以持续迭代的剧本工作台。

交互上，项目围绕“创建项目 -> 生成版本 -> 查看/编辑 -> 对比 -> 局部重生成 -> 保存新版本”的创作闭环设计。每一次 AI 输出都被保存、校验和追踪，确保用户可以理解、修改和回退。

这套设计的重点不是追求最复杂的技术栈，而是围绕小说改编的真实工作流，把 AI 的创造力和工程系统的确定性结合起来。

## 21. HTTP API 设计

### API 的设计目标

Web 工作台所有能力都通过本地 HTTP API 暴露。API 的目标不是对外开放成公共平台，而是为浏览器工作台、自动化脚本和后续扩展提供稳定边界。

当前 API 设计遵循几个原则：

1. 路径语义清晰，围绕 project、version、task 三类资源组织。
2. 返回结构统一，成功返回 `{ "ok": true, "data": ... }`，失败返回 `{ "ok": false, "error": ... }`。
3. 写操作创建新版本，不覆盖旧版本。
4. 长任务走异步接口，避免 HTTP 请求长时间阻塞。
5. 静态资源和 API 同一个服务提供，方便本地一条命令启动。

### 主要接口分类

| 分类 | 接口示例 | 设计意图 |
| --- | --- | --- |
| 健康检查 | `GET /api/health` | 前端启动时确认服务版本、启动时间、缓存后端 |
| 项目列表 | `GET /api/projects` | 加载左侧项目导航 |
| 模型列表 | `GET /api/models` | 根据 API Key 和 base url 获取可用 Qwen 模型 |
| 版本列表 | `GET /api/projects/{project_id}/versions` | 加载某项目所有历史版本 |
| 版本详情 | `GET /api/projects/{project_id}/versions/{version_id}` | 加载 YAML、结构化数据和预览信息 |
| 导出 YAML | `GET /api/projects/{project_id}/versions/{version_id}/export-yaml` | 下载或复制当前版本 |
| 版本对比 | `GET /api/projects/{project_id}/diff?from=...&to=...` | 对比两个版本的 YAML 差异 |
| 同步生成 | `POST /api/adapt` | 用于小输入或测试场景 |
| 异步生成 | `POST /api/adapt-async` | 用于 Web 正常生成流程 |
| YAML 重生成 | `POST /api/regenerate-from-yaml-async` | 基于已有 YAML 生成新版本 |
| 保存编辑 | `POST /api/projects/{project_id}/versions/{version_id}/save` | 把人工编辑后的 YAML 保存成新版本 |
| 场景重生成 | `POST /api/projects/{project_id}/versions/{version_id}/regenerate-scene-async` | 只重写一个场景 |
| 删除版本 | `DELETE /api/projects/{project_id}/versions/{version_id}/delete` | 删除不需要的本地版本 |
| 任务状态 | `GET /api/tasks/{task_id}` | 查询异步任务状态 |
| 任务流 | `GET /api/tasks/{task_id}/stream` | 用 SSE 推送任务状态 |

### 为什么 API 不直接暴露底层文件路径

版本文件实际保存在 `.novel2script` 下，但 API 不让前端直接操作文件路径。原因是：

- 前端不应该知道本地存储结构。
- 防止路径穿越和误删文件。
- 后续迁移到数据库时不影响前端。
- 所有写入都可以经过 Schema 校验和缓存失效。

API 使用 `project_id` 和 `version_id` 作为稳定资源标识，让存储实现保持可替换。

### 错误返回设计

服务端将常见错误区分为：

- `400 Bad Request`：请求参数缺失、YAML 格式错误、scene_id 缺失。
- `404 Not Found`：项目、版本、静态资源或路由不存在。
- `500 Internal Server Error`：未预期异常。

统一错误结构能让前端用同一套逻辑展示错误提示，而不是每个接口单独处理。

## 22. 前端状态设计

### 为什么前端状态集中在单个 `state` 对象

当前前端没有使用 React/Vue，所以需要一个简单的状态管理方式。项目使用集中式 `state` 对象保存：

- 当前项目。
- 当前版本。
- 上传文件信息。
- 当前任务。
- 当前模型/provider。
- 当前预览内容。
- 当前语言。
- 项目和版本列表。

这样设计虽然没有框架那么规范，但能避免状态散落在 DOM 上。每个交互事件都先更新 `state`，再调用渲染函数刷新界面。

### 主要交互状态

| 状态 | 触发场景 | 界面反馈 |
| --- | --- | --- |
| 未选择项目 | 首次进入页面 | 右侧显示生成入口或空预览 |
| 正在加载项目 | 刷新项目列表 | 按钮禁用或显示加载状态 |
| 正在生成 | 提交异步生成任务 | 生成按钮禁用，状态区显示任务进度 |
| 生成完成 | task completed | 自动加载新版本并刷新项目列表 |
| 生成失败 | task failed | 展示错误信息，允许用户修改输入后重试 |
| 编辑 YAML | 用户修改 YAML 文本 | 保存按钮可用 |
| 对比版本 | 选择两个版本 | 展示 diff 结果 |
| 场景重生成 | 输入 scene_id 和指令 | 显示局部重生成任务状态 |

### 为什么按钮需要禁用状态

AI 生成是长任务，如果用户重复点击生成按钮，会产生多个并发任务，导致：

- 重复消耗模型额度。
- 版本列表出现多个相似版本。
- 前端不知道应该展示哪个任务结果。

因此生成、重生成、保存等操作在请求中会设置禁用状态，请求结束后再恢复。

### 为什么交互不做复杂向导

生成剧本涉及很多参数，如果设计成多步骤向导，会让用户在第一版中被流程束缚。当前采用单页工作台：

- 左侧项目导航。
- 中间输入和控制。
- 右侧/下方预览和结果。

这样用户可以自由在生成、查看、编辑、重生成之间切换，更符合工具型产品。

## 23. 安全与边界设计

### API Key 处理

项目允许用户在 Web 端输入 DashScope/Qwen API Key，也支持从环境变量读取。

设计原则：

- 不把 API Key 写入 README、示例文件或版本库。
- Web 请求可以临时传入 API Key，用于本次模型调用。
- CLI 推荐使用环境变量 `DASHSCOPE_API_KEY` 或 `QWEN_API_KEY`。
- 本地版本中记录模型名称和 provider，但不记录真实密钥。

### 本地文件边界

Web 服务通过 `VersionStore` 操作 `.novel2script`，避免前端传任意路径直接读写。

上传文本会进入版本库或临时输入引用，不让用户通过 API 任意访问系统文件。

### 为什么没有做登录鉴权

当前项目定位是本地工作台，默认绑定 `127.0.0.1`。因此没有加入用户登录和权限系统。

如果部署到公网，必须补充：

- 用户认证。
- 项目权限。
- API Key 加密存储。
- 上传文件大小限制。
- 访问日志和审计。
- CSRF/CORS 策略。

当前设计避免假装已经具备云端安全能力，而是明确把它定位为本地工具。

## 24. 性能设计

### 主要性能瓶颈

项目性能瓶颈主要来自：

- 模型 API 响应时间。
- 多章节逐章分析。
- 长文本生成。
- YAML 解析和版本列表读取。
- 前端大文本渲染。

### 已采用的优化

1. 章节分析并发：多章节可并行调用。
2. 场景生成并发：多个场景可并行生成。
3. Hybrid 模式：不是所有阶段都走真实大模型。
4. 生成详细度：用户可选择 fast/standard/detailed。
5. Redis 缓存：缓存项目列表、版本详情、diff 等读操作。
6. 异步任务：避免长请求阻塞浏览器。
7. SSE 状态流：让用户知道任务仍在执行。

### 为什么不盲目提高并发

并发数不是越高越好。模型 API 通常有速率限制，本地机器也有资源限制。项目把并发 worker 限制在较小范围，是为了：

- 避免触发模型限流。
- 避免短时间创建过多网络请求。
- 保持本地演示稳定。
- 降低失败后重试成本。

### 后续性能优化方向

- 对章节摘要结果做持久缓存。
- 将长任务迁移到任务队列。
- 为模型调用增加指数退避重试。
- 对大 YAML 做虚拟滚动或分区渲染。
- 增加 token 预算估算，提前提示用户输入过长。
- 根据模型能力动态选择摘要和生成策略。

## 25. 可靠性设计

### 为什么每一步都保留回退

AI 输出不可控，因此系统在多个位置设置了回退：

- 章节解析失败时抛出明确错误。
- 大纲为空时根据章节分析生成 fallback scene plans。
- 三幕模板不合适时改为连续正文结构。
- 生成场景后做引用归一化。
- YAML 加载时支持 legacy payload 迁移到 schema 2.0。
- 质量检查会合并本地检查和 AI 审阅建议。

这些回退不是为了隐藏错误，而是为了让系统尽量产出可检查的草稿，同时通过 warnings 告诉用户风险。

### 为什么要记录任务错误日志

异步任务失败时，用户看到的是简短错误；开发者需要更详细的 traceback。项目在运行时目录记录任务错误，便于调试。

这种设计兼顾两点：

- 用户界面不显示过多技术细节。
- 开发者能定位真实异常。

## 26. 可维护性设计

### 模块边界

项目刻意避免把所有逻辑堆在 Web handler 中。HTTP 层只负责：

- 解析路由。
- 读取 JSON。
- 调用 `WorkbenchService`。
- 返回 JSON。

真正业务逻辑在服务层。这样做的好处：

- CLI 可以复用服务层。
- 测试可以绕过 HTTP，直接测服务。
- 后续换 Web 框架时，业务逻辑不用重写。

### 数据模型集中定义

所有核心 YAML 字段集中在 `models/schema.py`，运行时请求集中在 `models/runtime.py`。

这样可以避免多个模块各自定义类似结构，减少字段不一致。

### 文档与测试同步

Schema、README、API 流程和测试需要同步维护。因为 AI 项目变更很容易影响用户实际工作流，如果只改代码不改文档，演示和交付都会出问题。

## 27. 答辩讲解建议

如果需要向老师、评审或面试官介绍，可以按以下顺序讲：

1. 先讲问题：长篇小说直接交给模型生成剧本不可控，缺少版本、结构和局部修改能力。
2. 再讲方案：把任务拆成章节解析、故事设定、大纲规划、剧本生成、质量检查和版本保存。
3. 讲技术选型：Python 做 AI 编排，Pydantic 保证结构，YAML 便于编辑，Qwen 负责中文生成，Web/CLI 双入口方便不同用户。
4. 讲核心亮点：结构化 YAML、版本管理、YAML 重生成、单场景重生成、模型选择、异步任务。
5. 讲工程质量：Mock 模型测试、Schema 校验、缓存、Docker/Nginx/Redis 部署。
6. 讲后续扩展：多人协作、数据库版本库、角色关系图、分镜导出、任务队列。

### 一分钟版表述

本项目是一个面向小说改编的 AI 剧本工作台。它不是简单调用大模型生成一段文本，而是把小说拆成章节，先生成 Story Bible 和大纲，再生成结构化剧本 YAML，并把每次生成、编辑和重生成保存为可追踪版本。系统同时提供 CLI 和 Web 工作台，支持 Qwen 模型、Mock 演示、模型选择、异步生成、YAML 重生成和单场景重写。技术上用 Python 做编排，Pydantic 做 Schema 校验，YAML 保证人类可编辑，Redis/Nginx/Docker 提供可选部署能力。

### 三分钟版表述

这个项目解决的是长篇小说改编剧本时“生成不可控、结果不可编辑、修改不可追踪”的问题。整体流程分为输入解析、章节理解、故事设定、场景规划、剧本生成、质量检查和版本保存。输入小说后，系统会先按章节解析，再让模型或本地逻辑生成章节摘要、人物地点设定和大纲，最后生成剧本文本并结构化为 YAML。

我们选择 YAML 是因为它既能让作者直接编辑，又能通过 Pydantic 和 JSON Schema 做强校验。每个剧本文件包含 meta、source、adaptation、story_bible、outline、script、quality 和 extensions，保证离开系统后仍然自描述。版本管理使用本地 `.novel2script`，每次生成、保存、重生成都会创建新版本，避免覆盖历史。

交互上，Web 工作台提供项目列表、版本列表、生成表单、模型选择、YAML 预览、版本对比、YAML 重生成和单场景重生成。长任务通过异步任务和 SSE 状态流反馈进度。CLI 则用于开发者批处理和测试。技术选型上，Python 适合 AI 编排，Pydantic 保证结构可靠，Qwen 适合中文生成，Mock 保证无 API Key 也能演示，Redis/Nginx/Docker 用于更完整的本地部署。

项目的重点是把 AI 的不确定输出放进一个可验证、可回退、可迭代的工程工作流中。

## 29. 版本演进说明

当前版本已经从最初的 CLI 生成工具，演进成具有 Web 工作台和版本化能力的本地创作系统。演进路线可以概括为：

1. 第一阶段：完成小说到 YAML 剧本的 CLI 生成。
2. 第二阶段：增加 Web 工作台，支持浏览器生成、查看和下载。
3. 第三阶段：增加版本管理、diff、保存编辑和单场景重生成。
4. 第四阶段：接入 Qwen、模型选择、生成详细度和异步任务。
5. 第五阶段：增加 YAML 重生成，让已有剧本也能继续迭代。
6. 第六阶段：增加 Redis/Nginx/Docker/Windows 本地三层运行方案。

这个演进路径体现了产品从“能生成”到“能持续创作”的变化。
